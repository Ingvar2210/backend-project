From a static guide to saved notes

An interactive account of the backend, data model, security review, and the changes visitors can see. Select a topic below.

What this project needs

The original interactive guide teaches CSS framework concepts. A study notes feature gives the backend a useful job: readers can keep their own questions and examples while learning. The Bootstrap and Tailwind pages remain visual comparisons.

Assumption: this is a small, single-server classroom demo. It has no accounts, collaboration, or cloud deployment requirement. If those needs change, revisit storage and identity.

Why SQLite?

SQLite · chosen

One database file, SQL tables, transactions, and no separate database service. Notes have predictable fields and an owner ID, so a relational table fits cleanly.

PostgreSQL

A good choice for multiple app servers, managed hosting, more concurrent writes, and richer operational tools. It adds a service and credentials this demo does not need.

MongoDB

Useful for flexible document structures. This note schema is small and stable, so document storage brings no clear benefit here.

Hard topic: the database file is durable only where the server’s data/ folder persists. Ephemeral hosting can erase it. Back up the file and its write-ahead log consistently, or use a persistent volume.

Why Node.js without a framework?

The existing pages already use browser JavaScript. Node.js 24 serves them and provides a built-in SQLite API, HTTP server, and crypto functions. One language and zero npm runtime packages keep this exercise small.

Express would be a sensible next step if routing and middleware grow. Next.js adds a React app structure and rendering model the existing static pages do not need. Bun, Rust, Ruby, and PHP can all serve this feature, but would add a new runtime or language without a concrete benefit for this repository.

Security review and fixes

  • SQL injection: prepared statements bind user values; IDs are numeric and checked.
  • Cross-site scripting: note text is inserted with textContent, not HTML. A content security policy and other response headers add defense.
  • Unauthorized access: a random, HttpOnly, SameSite=Strict browser cookie identifies the note owner; SQL queries include its hash. Changing a URL ID cannot read another browser’s note.
  • Cross-site requests: writes require a matching Origin header. The cookie gains Secure in production, where HTTPS is required.
  • Bad input: JSON type, required strings, and length limits are checked server-side; requests have a size cap.
  • Static files: only known paths are served, preventing path traversal into the database or server code.

Identity trade-off: the cookie is an anonymous capability, not a login. Clearing it loses access; anyone who obtains it can act as that browser. This is suitable for low-stakes study notes, not private or sensitive data. For real accounts, use a mature identity provider or passwordless login with server-side sessions, account recovery, and rate limits. Avoid building password storage as a classroom shortcut.

Remaining deployment work: set up HTTPS, persistent storage and backups, request rate limiting at a trusted proxy, and a production Tailwind build. The existing Tailwind page uses the browser CDN for the demo. No external penetration test was performed.

What changed for visitors?

Before, each page was read-only and could run as a file. Now the hub links to Study notes, where a form, note list, edit state, delete confirmation, and clear status messages support CRUD. Saved notes return after a refresh in the same browser.

The site now needs npm start and a persistent server; opening HTML files directly cannot use the API. The existing Bootstrap and Tailwind visual demos retain their layouts. The new notes page follows the lab’s purple palette and uses labels, keyboard focus, and live status text for accessibility.
